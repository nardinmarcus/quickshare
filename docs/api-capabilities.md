# Share API identity and capabilities

`GET /api/v1/me` and `GET /api/v1/capabilities` require `X-API-Key`. Dashboard/login/access cookies never substitute for a Key. Missing or invalid Keys return 401; database authentication failure returns 503. Responses are private/no-store. Discovery remains available during publishing maintenance; best-effort usage timestamps neither authorize writes nor delay discovery.

`/me` returns `success`, canonical instance `origin` (the origin of `BASE_URL`, otherwise the request origin), `credentialKind` (`legacy` or `managed`) and `scopes` — the operation vocabulary this credential may ask for. Managed identities additionally expose `id`, `name`, and decimal-string `credentialVersion`. No secret, hash, grants or other resources are returned. A Key identifies a credential, not Share ownership. Legacy keys always answer `scopes: ["share:create"]`.

`/capabilities` returns `success`, `protocolVersion`, `contentTypes`, `markdownThemePresets`, `limits`, and `operations`. **The executable definition is `utils/apiCapabilities.js`**, shared by the Express content-type validation, request parsers, create route, discovery response and rendered `/admin/apis` documentation. The Preset IDs come directly from `utils/markdownThemeCatalog.js`; there is no independent documentation catalog to maintain. Query the instance for its current values rather than copying an older list.

- Scopes and per-Share grants (#36, implemented): the scope vocabulary is `share:create`, `share:read`, `share:update`, `share:publish`; only `create` and `read` exist today and `/capabilities` reports exactly that under `scopes.implemented` / `scopes.notImplemented`. Managed keys are born create-only; the owner grants read access per Share from `/admin/apis`, and a key's first read grant unlocks the `share:read` scope while revoking the last one removes it again. A successful grant withdrawal audits as `api_key.revoke` and withdraws only that Key–Share read authorization. Permission is always scope AND grant: an authenticated key without the scope gets 403, a scoped key without the grant for the target gets a 404 identical to a missing Share. Three read-only resource endpoints exist over `X-API-Key`:
  - `GET /api/v1/shares` — paginated list of granted Shares (default 20, max 100, stable cursor over `(created_at, id)`; invalid cursor/limit is 400). Metadata only: no body, no password material, no Favorite state.
  - `GET /api/v1/shares/:id/content` — full snapshot of the CURRENT revision (`id`, `revision`, `htmlContent`, `codeType`, `title`, `description`, `markdownTheme`) with strong ETag `"content:<id>:<revision>"`; `If-None-Match` matching it answers 304.
  - `GET /api/v1/shares/:id/state` — `published`, `isProtected`, `expiresAt`, `accessRevision` with the independent strong ETag `"access:<id>:<accessRevision>"`; it never carries title, description or body.
  Unpublished, password-protected and expired Shares stay readable for granted keys — management authorization is independent of public visibility. Every response is private/no-store; cookies and public viewing rights never authorize these APIs. History purge remains dashboard-only with no API surface.
- Both credential kinds remain create-only for WRITES: the Share write operations are `share:create` (`POST /api/v1/share`) and its status confirmation `share:create:status` (`GET /api/v1/operations/:requestId`, metadata only). Conditional update, history and publish-state protocols are NOT implemented; `share:update` / `share:publish` stay listed as not-implemented until their tickets (#37/#39). History purge exists ONLY behind the owner dashboard (signed dashboard session + CSRF + exact Share+revision confirmation); it has no `X-API-Key` surface, no scope, and no CLI entry, and this API's capability surface deliberately never exposes it.
- **Create idempotency (implemented, create-only):** new clients generate UUID v4 request ids and send an `Idempotency-Key` header matching `^[A-Za-z0-9_-]{16,128}$` with every create. The same key with the same normalized input confirms the committed result (`replayed: true`) — the response carries the ORIGINAL creation metadata from the encrypted receipt, never the owner's later edits; the same key with different input (values or field presence) is `409 REQUEST_ID_CONFLICT`. Requests are scoped to a credential namespace (managed logical key id, irreversible legacy secret fingerprint, or the browser's signed publish session), so the same id in another namespace is a new operation. Result availability (Share AND committed revision) is re-checked before confirmation: tombstoned, deleted or purged results answer `410 RESULT_UNAVAILABLE` without leaking metadata and never rebuild. Replays never return generated passwords after the Share's access policy changed. Omitting the header keeps the legacy unmarked behavior, which is NOT claimed to be deduplicated. Management writes beyond create + status are not offered. The owner dashboard separately gained idempotent content saves and history restores over Cookie + CSRF (#33) and idempotent unpublish/republish transitions over Cookie + CSRF + required `Idempotency-Key` + required `expectedAccessRevision` (#35); those surfaces are Cookie-gated, never available through `X-API-Key`, and change nothing in this API's capability surface — the `share:publish` scope and publish-state endpoints (`unpublish`/`republish` over a Key) remain a later ticket (#39) and are deliberately NOT advertised here.
- `shareRequestBodyBytes` and `smallRequestBodyBytes` report actual configured parser limits (default 2mb and 16kb). These count the decoded HTTP request body including JSON structure, metadata and escape sequences. `rawContentBytes: null` means no separate fixed raw-content capacity is advertised. Transport/proxy limits may be lower. Exceeding the application parser limit returns 413.
- The legacy create endpoint retains status 200 and existing `success`, `url`, `urlId`, `password`, `isProtected`, `codeType`, `title`, `description`, `expiresAt`, `markdownTheme` fields. It does not expose Favorite Share state.

## Managed Key rotation

The owner uses `/admin/apis` or `POST /admin/apis/keys/:id/rotate` with a dashboard session and CSRF token. Successful rotation preserves ID/name/created time/prefix, replaces the secret hash and increments BIGINT `credential_version`. The receipt's `apiKey.credential_version` is a decimal string and `apiKey.secret` contains the new full Key. Only a committed successful receipt discloses it; reload/listing cannot recover it. Creation and deletion remain supported. Legacy environment Keys cannot be rotated through this endpoint.

Share authentication captures the version paired with the first verified hash. Inside the existing publishing transaction, lock order is maintenance gate → Key row → Share write/audit. Rotation UPDATE and deletion DELETE take that same Key row lock. If rotation/deletion commits first, the old request returns 401 without creating a Share. If the legitimate write takes the lock first, it may commit before rotation; revocation does not undo already committed work. SQL/audit/COMMIT failures roll back the transaction and never return a successful credential receipt.

Migration `006` adds the positive BIGINT version with default 1, preserving existing IDs and hashes; migration `010` adds the `scopes`/`auto_grant_new_share_edit` columns (existing rows backfilled to create-only) and the `share_grants` table. Grants reference the Key's logical identity: rotation keeps every grant, deleting the Key or the Share cascades them away, and native backups compare `scopes`, `auto_grant_new_share_edit` and every `share_grants` row by name. Follow the maintenance and rollback instructions in [deployment](deployment.md); never roll back to a credential-version-ignorant writer. Native backups compare `credential_version` explicitly and treat post-snapshot `api_key.revoke`, `api_key.delete` and `api_key.rotate` as hard authorization-revocation signals. They are distinct: `api_key.revoke` withdraws one Share read grant, `api_key.delete` removes the Key and cascades all its grants, and `api_key.rotate` replaces its secret while preserving the logical Key ID and grants. A snapshot predating any of these events may restore revoked access (or an old credential); verification names the event and reports `unreconciled`, requiring owner reconciliation before serving. `--reconciled` affects only the process exit code; it writes no review/acknowledgment marker to the report and does not change its `safeToServe: false` value.
