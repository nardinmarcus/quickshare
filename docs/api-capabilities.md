# Share API identity and capabilities

`GET /api/v1/me` and `GET /api/v1/capabilities` require `X-API-Key`. Dashboard/login/access cookies never substitute for a Key. Missing or invalid Keys return 401; database authentication failure returns 503. Responses are private/no-store. Discovery remains available during publishing maintenance; best-effort usage timestamps neither authorize writes nor delay discovery.

`/me` returns `success`, canonical instance `origin` (the origin of `BASE_URL`, otherwise the request origin), `credentialKind` (`legacy` or `managed`) and `scopes` — the operation vocabulary this credential may ask for. Managed identities additionally expose `id`, `name`, and decimal-string `credentialVersion`. No secret, hash, grants or other resources are returned. A Key identifies a credential, not Share ownership. Legacy keys always answer `scopes: ["share:create"]`.

`/capabilities` returns `success`, `protocolVersion`, `contentTypes`, `markdownThemePresets`, `limits`, and `operations`. **The executable definition is `utils/apiCapabilities.js`**, shared by the Express content-type validation, request parsers, create route, discovery response and rendered `/admin/apis` documentation. The Preset IDs come directly from `utils/markdownThemeCatalog.js`; there is no independent documentation catalog to maintain. Query the instance for its current values rather than copying an older list. This repository has no OpenAPI source; the executable capability definition and these route docs are authoritative, and no separate OpenAPI contract is claimed.

- Scopes and per-Share grants (#36–#38, implemented): the scope vocabulary is `share:create`, `share:read`, `share:update`, `share:publish`; `/capabilities` reports create/read/update under `scopes.implemented` and only publish under `scopes.notImplemented`. Managed keys are born create-only. The owner may grant read or edit per Share from `/admin/apis`; edit always implies read. First/last grants manage the corresponding scopes, and every grant mutation is audited. A successful complete-grant withdrawal audits as `api_key.revoke`; it withdraws that Key–Share permission. Permission is always scope AND grant: an authenticated key without the required scope gets 403, a scoped key without the grant for the target gets a 404 identical to a missing Share. Read-only resource endpoints over `X-API-Key` are:
  - `GET /api/v1/shares` — paginated list of granted Shares (default 20, max 100, stable cursor over `(created_at, id)`; invalid cursor/limit is 400). Metadata only: no body, no password material, no Favorite state.
  - `GET /api/v1/shares/:id/content` — full snapshot of the CURRENT revision (`id`, `revision`, `htmlContent`, `codeType`, `title`, `description`, `markdownTheme`) with strong ETag `"content:<id>:<revision>"`; `If-None-Match` matching it answers 304.
  - `GET /api/v1/shares/:id/state` — `published`, `isProtected`, `expiresAt`, `accessRevision` with the independent strong ETag `"access:<id>:<accessRevision>"`; it never carries title, description or body.
  - `GET /api/v1/shares/:id/revisions` — default 20 / max 100, descending exact-BIGINT keyset cursor. Returns only revision/time/source/restore-origin/current/purged metadata; never a title, body, hash, credential, grant or Favorite field. A newly-created higher revision does not shift an existing cursor walk.
  - `GET /api/v1/shares/:id/revisions/:revision` — one authorized canonical snapshot only; revisions are decimal strings, a purged tombstone is 410 with non-content identity only, and an unknown revision is 404.
  Unpublished, password-protected and expired Shares stay readable for granted keys — management authorization is independent of public visibility. Every response is private/no-store; cookies and public viewing rights never authorize these APIs. History purge remains dashboard-only with no API surface.
- Implemented write operations are `share:create` (`POST /api/v1/share`), `share:content:update` (`PUT /api/v1/shares/:id/content`), and `share:restore` (`POST /api/v1/shares/:id/restore`); the shared metadata-only status endpoint is `GET /api/v1/operations/:requestId`. Update and restore require a managed Key, both read and update scopes, and the matching per-Share read+update grant. Restore also requires a concrete strong current-content `If-Match` and `Idempotency-Key`; its source is one positive integer or canonical decimal string, and the digest includes both source and current baseline. Fresh restore uses the existing locked dashboard CAS/no-op/revision/audit ledger path, writes `source='api-restore'` / `actor='api-key:<id>'`, and never changes URL or access policy. A matching replay precedes stale CAS only after current Key/grant checks; purged source/result means 410 and never revives receipt data. Legacy environment keys remain create-only. The owner may opt a managed Key into auto-granting read+edit to only its subsequent creations; this is off by default, does not affect browser/legacy creation, and never retroactively changes existing Shares. Publish-state API writes are NOT implemented; `share:publish` remains not-implemented. History purge exists ONLY behind the owner dashboard (signed dashboard session + CSRF + exact Share+revision confirmation); it has no `X-API-Key` surface, no scope, and no CLI entry, and this API's capability surface deliberately never exposes it.
- **Idempotency:** `POST /api/v1/share` keeps its backward-compatible optional header; new clients should send a UUID v4 `Idempotency-Key` matching `^[A-Za-z0-9_-]{16,128}$`. Conditional `PUT /api/v1/shares/:id/content` and `POST /api/v1/shares/:id/restore` require that header and a concrete strong content `If-Match` ETag. Restore body is exactly `{ "revision": <positive safe integer or canonical decimal string> }`. Same key + same normalized input confirms the committed original result (`replayed: true`); same key + different input (including baseline/source) is `409 REQUEST_ID_CONFLICT`. Stale content baselines are `412`; missing precondition/idempotency headers are `428`. Update/restore replay is checked only after the current Key and edit grant are revalidated. Restore result or source purge is `410 RESULT_UNAVAILABLE`; an individual tombstone read is `410 REVISION_PURGED`. The request body and encrypted receipt are never returned by operation status; restore status also rechecks current edit authorization and source/result availability. All operations are scoped to a credential namespace, so the same ID in another namespace is independent. Create replay keeps the ORIGINAL creation metadata behavior. The owner dashboard separately provides idempotent content saves, history restores (#33) and publish-state transitions (#35) over Cookie + CSRF.
- `shareRequestBodyBytes` and `smallRequestBodyBytes` report actual configured parser limits (default 2mb and 16kb). These count the decoded HTTP request body including JSON structure, metadata and escape sequences. `rawContentBytes: null` means no separate fixed raw-content capacity is advertised. Transport/proxy limits may be lower. Exceeding the application parser limit returns 413.
- The legacy create endpoint retains status 200 and existing `success`, `url`, `urlId`, `password`, `isProtected`, `codeType`, `title`, `description`, `expiresAt`, `markdownTheme` fields. It does not expose Favorite Share state.

## Managed Key rotation

The owner uses `/admin/apis` or `POST /admin/apis/keys/:id/rotate` with a dashboard session and CSRF token. Successful rotation preserves ID/name/created time/prefix, replaces the secret hash and increments BIGINT `credential_version`. The receipt's `apiKey.credential_version` is a decimal string and `apiKey.secret` contains the new full Key. Only a committed successful receipt discloses it; reload/listing cannot recover it. Creation and deletion remain supported. Legacy environment Keys cannot be rotated through this endpoint.

Share authentication captures the version paired with the first verified hash. Inside the existing publishing transaction, lock order is maintenance gate → Key row → operation row → Share/grant rows → write/audit. Rotation UPDATE and deletion DELETE take the same Key row lock. If rotation/deletion commits first, the old request returns 401 without writing content. If the legitimate write takes the lock first, it may commit before rotation; revocation does not undo already committed work. SQL/audit/COMMIT failures roll back the transaction and never return a successful credential receipt.

Migration `006` adds the positive BIGINT version with default 1, preserving existing IDs and hashes; migration `010` adds the `scopes`/`auto_grant_new_share_edit` columns (existing rows backfilled to create-only) and the `share_grants` table. Grants reference the Key's logical identity: rotation keeps every grant, deleting the Key or the Share cascades them away, and native backups compare `scopes`, `auto_grant_new_share_edit` and every `share_grants` row by name. Follow the maintenance and rollback instructions in [deployment](deployment.md); never roll back to a credential-version-ignorant writer. Native backups compare `credential_version` explicitly and treat post-snapshot `api_key.revoke`, `api_key.auto_grant_new_share_edit.disable`, `api_key.delete` and `api_key.rotate` as hard authorization-revocation signals. They are distinct: `api_key.revoke` withdraws one or more grants for a Share, the auto-edit disable prevents future broad grants from being silently re-enabled, `api_key.delete` removes the Key and cascades all its grants, and `api_key.rotate` replaces its secret while preserving the logical Key ID and grants. A snapshot predating any of these events may restore revoked access (or an old credential); verification names the event and reports `unreconciled`, requiring owner reconciliation before serving. `--reconciled` affects only the process exit code; it writes no review/acknowledgment marker to the report and does not change its `safeToServe: false` value.
