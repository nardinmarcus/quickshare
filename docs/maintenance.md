# 发布写维护模式（运维手册）

写维护模式用于给发布、迁移和备份提供一个真实的切换点：暂停之后可以确认
既有发布事务已经全部结束，后续安全迁移从一个静止、一致的状态开始。

## 开关与语义

- 开关是站点设置里的 `publishing_writes_paused`（迁移 `005` 引入），默认
  `false`。它**只能**通过受控运维方式（本页的 CLI）修改，后台界面和普通
  用户设置里没有这个选项；每次实际切换都会写入审计
  `settings.publishing_writes_paused.update`。
- 所有发布写入口共用同一道维护闸：创建、后台编辑、保护/撤销、克隆、删除
  （单个与批量）、收藏、API Key 创建/删除、站点设置写入，以及
  `backfill-page-titles.js --write`。写事务先取得闸的共享锁再检查开关，
  同一数据库事务内完成，内存 Adapter 行为一致。
- 已暂停时写入被拒绝：
  - HTTP 入口返回明确的维护 `503`，响应体为
    `{"success": false, "error": "Publishing is paused for maintenance", "code": "maintenance", "retryable": true}`；
  - 浏览事件（view-event）返回 `503` 且**不计数**；
  - 与排空竞争失败的写入（锁等待超时/死锁）同样以可重试的 `503` 返回，
    不会留下半写状态。
- 暂停期间保持可用：公开读取与 Share 查看、访客密码解锁、已认证的后台
  只读页面与登录。API Key 的最近使用时间这类后台记账更新不走维护闸，不
  会妨碍读取。

## 操作

```bash
# 查看当前状态
npm run db:maintenance -- status

# 进入维护（排空）：等待全部在途发布事务结束后才返回
npm run db:maintenance -- pause

# 恢复写入
npm run db:maintenance -- resume
```

`pause` 返回成功意味着排空已完成：它在闸上取得排他锁，此前已进入的发布
事务必须先提交或回滚，排他锁才会被授予；暂停生效后启动的写入只会读到
`publishing_writes_paused = true` 并被拒绝。因此「pause 成功返回之后，不
会再有先前未结束的发布事务提交新内容」。`pause` 输出的 `durationMs` 包含
排空等待时间，属于正常现象，不要因为等待而重复执行或强杀。

## 发布/迁移流程中的用法

1. 先完成完整备份（见 [备份与恢复](backup-restore.md)），并部署认识维护
   闸的应用版本（本票及之后版本），验证未暂停时发布功能正常。
2. 执行 `npm run db:maintenance -- pause` 并确认返回成功。
3. **确认旧部署已退出可写路径**：所有还在运行的旧版本实例（不认识维护
   闸、会绕过闸直接写入）必须停止或下线。滚动部署期间新旧混合运行不等于
   旧请求已经结束。**若无法确认旧写入者已经全部退出，则维持维护状态、不
   继续迁移**，先解决旧写入者隔离问题。
4. 在维护状态下执行迁移（`npm run db:migrate`）与核对。
5. 部署目标版本并完成检查后，执行 `resume` 恢复写入，抽查创建、编辑、
   浏览计数恢复正常。

## 回滚与恢复注意事项

- 维护闸是数据与协议的一部分：回滚目标只能是认识访问版本与维护闸的兼容
  应用；在维护状态下出问题时优先向前修复，不要回滚到忽略维护闸的旧版本
  继续写入，也不要做破坏性 down migration 删除 `005` 列。
- 从备份恢复出的数据库会保留备份时刻的 `publishing_writes_paused` 值；演
  练已覆盖「备份时暂停、恢复后仍暂停」。恢复库在核对完成前保持
  `safeToServe: false`（见备份手册），不要因为开关为 `false` 就直接对外
  服务——先按备份手册核对恢复点之后的撤销与策略变更。

## 故障排查

- CLI 报 `publishing_writes_paused is missing`：目标库未执行迁移 `005`，
  先运行 `npm run db:migrate`。
- 写入偶发 `503`（`code: "publishing_unavailable"`）：与排空发生锁竞争且
  等待超时，写入未生效，使用原参数重试即可；不要并发发起暂停/恢复切换。
- `pause` 长时间不返回：有发布事务长时间未结束（或旧版本写入者仍在持续
  写入）。先定位长事务来源，不要强行改库绕过闸。
